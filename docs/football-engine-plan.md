## 一、文獻研究結論（可為我們所用的部分）

### 1.1 建模路線比較（賽前 1X2）

| 路線 | 輸入 | 對我們的用法 | 判斷 |
|---|---|---|---|
| Elo / pi-rating | 只需歷史比分 | **直接對應「天喜ELO」**；pi-rating 對主／客場分開評分、非對稱學習率 | 採用（作特徵，不作終端） |
| Poisson / Dixon-Coles | 攻防強度 α/β、主場係數、時間加權 | 產生完整比分分布 → 一次過供 1X2、大小球、亞盤 | 採用（作先驗特徵） |
| 雙變量 Poisson | 加共同分量建進球相關 | 比 DC 更一般化，但參數多、小樣本不穩 | 備選 |
| GBDT（LightGBM） | 混合表格特徵 | **直接對應「天喜LGB」**；文獻結論：GBDT 套在 pi-rating 特徵上是純比分資料集的最佳組合 | 採用（主體） |
| 序列模型 / GNN | 事件級、追蹤資料、傳球網絡 | 需要事件級資料，公開文獻未見在純賽前 1X2 穩定勝出 | 暫不做 |
| 混合集成 | Poisson 機率 + Elo 差 → GBDT → 校準 | **與我們賽馬的 ELO→LGB→z-score→α 集成→校準 完全同構** | 採用 |

關鍵教訓：多份比較研究指出 **ML 與 Poisson 的演算法本身差距很小**，ML 的優勢來自「能吃非進球特徵」（xG、傷停、賽程密度）。所以資料層比模型層重要 —— 與我們賽馬引擎的經驗一致。

### 1.2 基準與 gate 門檻（照賽馬「四揀平均中匹」的做法立一條硬指標）

| 基準 | 1X2 類別平均 Brier | 意義 |
|---|---|---|
| 均勻猜 1/3 | ≈ 0.222 | 理論下限對照 |
| 純歷史先驗（主/和/客比例） | ≈ 0.215 | **必過門檻**：過不了就等於無價值 |
| 去水收盤賠率 | ≈ 0.189 | **目標門檻**：達到即等同成熟市場水準 |
| 收盤市場 top-label ECE | ≈ 2% | 校準品質目標 |

以上數值來自單一非同行評審來源（Football Proof AI，2026），**必須在我們自己的英超資料上重新計算**這三條線，才可作為正式 gate。

主指標定案（對應賽馬的「四揀平均中匹 3/4」）：
1. **RPS（Ranked Probability Score）為第一指標** —— 1X2 是有序結果（和局介於主客勝之間），Brier／log-loss 不區分錯得多遠，2017 Soccer Prediction Challenge 因此建議優先報 RPS。
2. 輔助：類別平均 Brier、log-loss、逐類別 ECE（主／和／客，10-bin 可靠度圖）。
3. **不以 accuracy 為賣點** —— 和局基準率僅約 23–25%，永不預測和局都可以有不錯 accuracy，會誤導（同我們賽馬「不標榜首選命中率」原則一致）。

### 1.3 校準（直接沿用賽馬第四階段成果）

- Platt scaling（樣本小時）／isotonic（樣本大時），只調機率、不改排序 —— 與我們賽馬「market_beta=0、賠率零排名權重」原則相容。
- 有研究專門指出：投注決策依賴**校準品質**而非判別力，校準應納入模型選擇準則而非只做後處理。
- 一個德甲案例：簡單 xG + Skellam + isotonic 校準即可找到市場訊號 —— 證明先做好資料與校準，比堆模型複雜度更值。

### 1.4 資料洩漏陷阱（回測必守，賽馬版同樣適用）

1. 滾動 xG 未 `shift`，把當場 xG 算進了自己的近況均值。
2. 傷停用「賽後確認」版本，而非賽前公布時間戳版本。
3. 用**收盤賠率**做特徵 → 等於偷了臨場消息，回測必虛高。
4. 排名／積分未 shift 一輪。
5. 標準化在全資料集（含測試期）上算均值標準差。
6. Elo 參數用全歷史重擬合，而非截至當時逐場迭代。
7. 球隊 embedding／聚類用了含未來賽季的全資料訓練。
8. 和局類別做 SMOTE 時把測試集一起處理。
9. 賽程密度用事後改期日期 vs 原定日期，定義必須一致。

**與賠率比較時必須同一凍結時間點**（例如都用 T-24h 快照），不可用模型的早期預測去比收盤賠率。

### 1.5 回測設計

- 嚴格按日期滾動切分，**禁止 K-fold**。
- Elo/Poisson 每輪（gameweek）更新；LGB 每賽季或半季重訓，避免頻繁重訓帶來雜訊。
- 樣本外至少 1–2 個完整賽季，並**逐賽季報指標波動**，不接受單季結論。

### 1.6 附註（來源核對）

- 你給的 `arXiv:2512.12116v2` 實際內容是 Neural CDE 時間序列修正器，與足球無關，可能編號有誤。
- `arXiv:2607.18084v1` 是 WorldCupArena，評測 LLM／deep-research agent 的足球預測基準；它的「凍結時間點防洩漏」與「賽事層級聚合」評測協議設計可借用，但量化結果不能當 ML baseline。
- ResearchGate 那篇未能直接定位原文，如有 DOI 可再補核。

結論（英超先跑通的三源組合）：
1. **football-data.co.uk** = 賽果 + 歷史賠率骨幹（1993 至今，做 gate 基準用的收盤賠率就在這裡）。
2. **Understat**（xG，2014/15 起）先接一個；FBref 之後補。
3. **api-football 免費層** = 未來賽事的傷停／陣容。

歷史深度分層說明（要在產品上講清楚，同賽馬「資料覆蓋」欄一樣）：
- 1993–2014：只有比分＋賠率 → 只能訓練 Elo/pi-rating/Poisson。
- 2014/15 起：有 xG → 可以訓練完整 LGB 特徵集。
- 近 3 賽季：有傷停／陣容 → 陣容類特徵只在此區間可用，回測需分段報告。

### 2.2 特徵清單（全部賽前 as-of，凍結點 T-24h 與 T-1h 兩版）

- **A 球隊實力**：Elo（主客調整）、pi-rating（主／客獨立）、聯賽排名／積分（shift 一輪）、近 N 季強度基線、市場身價。
- **B 近況滾動**：近 3/5/10 場加權勝率、進失球、控球滾動均值；動能斜率；H2H 加權；**主客場分開統計**。
- **C 攻防 xG**：近 N 場 xG／xGA 均值與方差、xG 超額（實際進球 − xG，衡量運氣迴歸）、大機會創造／被創造。
- **D 陣容傷停**：傷停／停賽人數、關鍵球員缺陣旗標（分位置）、陣容深度、輪換頻率。
- **E 賽程與旅程**：rest days、近 X 天場次密度、跨賽事（聯賽／盃賽／歐戰）連戰、客場距離／時差、賽季階段動機因子。
- **F 主場優勢**：動態估計係數（空場期已證實需調整）、上座率代理。
- **G 天氣場地**：氣溫、降雨、風速、草皮 —— **直接沿用我們賽馬的天氣存檔管線寫法**（cron 只在比賽窗口內存檔）。
- **H 裁判**：主裁歷史黃紅牌／12 碼頻率、主場哨傾向。
- **I 市場賠率**：**只作對照與 gate 基準，排名權重為 0**（同賽馬 `market_beta=0` 原則）。若日後要入模，只准用開盤賠率並先過 gate。

### 2.3 自動化更新（你最未諗通的另一點）

分層（bronze / silver / gold），照賽馬 `tianxi-database` 的做法擴充：

```text
GitHub Actions (cron, UTC)
  ├─ bronze  原封不動存下載檔（CSV/JSON/HTML）＋抓取時間戳＋來源 URL
  ├─ silver  欄位標準化、型別轉換、球隊名經 bridge 表對齊 canonical_id、去重、缺值標記
  ├─ gold    特徵表（Elo、滾動 xG、Poisson 攻防參數、賠率隱含機率）
  └─ 服務層  D1（前端查詢）＋ 訓練副本（特徵工程／walk-forward）
```

增量策略（各源不同）：
- football-data.co.uk：**無單場 API，只能整季 CSV 覆蓋下載** → 每次下載後與上次快照 diff（key = `Date+HomeTeam+AwayTeam`），只 upsert 變動列。
- Understat／FBref：按賽季＋聯賽頁抓，用內容 hash 判斷有無新場次。
- api-football：有 `fixtures?date=` → 真正增量，最省請求數（免費層 100/day 必須省）。

**球隊名稱對齊（最痛的一環）**：`Man United` / `Manchester United` / `Manchester Utd`。
1. 建 `team_mapping(canonical_team_id, source, source_team_name, valid_from, valid_to)`。
2. 初次用 `rapidfuzz` 產生候選，人工審核後寫入（一次性成本）。
3. silver 層一律經此表轉 canonical_id；**匹配不到的丟入待處理隊列並告警，絕不靜默丟棄**。
4. 帶時間區間處理升降級與改名。

排程建議：
- **每日 06:00 UTC**：抓昨日完賽的賽果／賠率／xG；更新未來 7 天賽程的傷停陣容。
- **每週一凌晨 UTC**：全量重抓當季 CSV 做完整性校驗與補漏，跑完整資料品質報告。
- **賽季初／轉會窗**：手動觸發 `team_mapping` 更新（升班馬、改名）。
- **賽前 T-24h 與 T-1h**：兩次特徵凍結快照（供回測與「最終預測鎖定」用，同賽馬開跑前鎖定機制）。

資料品質告警（照賽馬 14 表紅黃綠警報做）：
- 每輪應有場次數 vs 實抓場次數（英超每輪 10 場）。
- 關鍵欄位空值率突增（賠率欄空值率上升＝莊家下架或頁面改版）。
- 數值合理性（賠率 <1.01 或 >1000 視為異常）。
- parser 失敗 / HTTP error → webhook 通知。
- 資料落後天數（同賽馬「晨操落後 52 日」那類告警）。

服務層取捨：
- **D1**：邊緣低延遲、免費額度大 → 前端查詢與展示層。
- **Postgres（Lovable Cloud）**：複雜 join、window function、大量歷史特徵工程 → 訓練與回測。
- 做法：gold 特徵存 Postgres 供訓練，彙總結果同步一份入 D1 供前端 —— 與現有賽馬架構一致。

## 四、分階段落地（每階段都有 gate，過不了不上線）

**S0 基建（第 1 週）**
建三倉、D1 資料庫、`team_mapping`、bronze/silver/gold 目錄與 Actions 骨架。
產出：英超 1993–2026 全量賽果＋賠率入庫。

**S1 基準線（第 2 週）**
在自有資料上算出三條基準：均勻猜、歷史先驗、去水收盤賠率的 RPS／Brier／log-loss／ECE。
Gate：三條基準數值定案並寫入文件，之後所有模型與此比較。

**S2 天喜足球ELO（第 3 週）**
Elo + pi-rating（主客獨立、非對稱學習率），逐場迭代更新，禁止全歷史重擬合。
Gate：RPS 優於歷史先驗。

**S3 Poisson / Dixon-Coles（第 4 週）**
時間加權攻防參數 → 完整比分分布 → 1X2 邊際機率。同時保留 DC 的 ρ 修正作 A/B（文獻顯示近年英超 DC 對比純 Poisson 的改善在統計雜訊內，不預設它更好）。
Gate：優於 S2，且比分分布可同時供未來大小球／亞盤使用。

**S4 天喜足球LGB（第 5–7 週）**
LightGBM 吃 §2.2 全特徵 + S2/S3 產出的先驗特徵。walk-forward、逐賽季報指標。
Gate：RPS 顯著優於 S3，且逐賽季波動可接受。

**S5 集成與校準（第 8 週）**
場內 z-score → α 集成（照賽馬 `blendZ = α·lgbZ + (1−α)·eloZ`）→ Platt／isotonic 校準（只調機率）。α 由回測掃描定，並沿用賽馬的 α 保護閘門（閘門失敗時維持現值＋標紅，不自動歸零）。
Gate：類別平均 Brier 逼近 0.189 區間、逐類別 ECE ≤ 3%。

**S6 產品化（第 9–10 週）**
紅黃綠燈鎖定流程（T-24h 暫定 → T-1h 鎖定 → 賽後對帳）、特徵選取頁（列出全部特徵，標採用／未採用／永不採用）、可靠度圖、殘差診斷、逐場解釋，全部照賽馬現有頁面套版。

**S7 擴展**
五大聯賽 → 大小球／亞盤 → 事件級資料（如取得授權）。

## 六、定案（2026-09-12 用戶決定）

### 6.1 賠率零權重（同賽馬一致）
`market_beta = 0`。賠率只有三個用途：①gate 基準線（去水收盤賠率的 RPS 是目標門檻）；②前端「市場對照」欄；③殘差診斷分層。**永不進入排名運算**。若日後要試，只准用開盤賠率、只准經 A/B，且必須先過 gate 才上線 —— 與賽馬 `market_beta` 流程完全相同。

### 6.2 球員級拆分：分兩層，不做「11 人分數直接相加」
用戶提出的問題本身就是關鍵限制：**中途換人 → 賽前無法確知實際組合**。所以拆到球員級只可以做成「賽前可觀測的球隊實力修正量」，不可以做成終端預測。

設計（三步，逐步 gate）：

1. **球員 Elo（天喜足球球員ELO）**：每名球員一個評分，逐場迭代更新，更新幅度按上場分鐘數加權（踢 90 分鐘全額、替補 20 分鐘只佔比例）。位置分開（門將／後衛／中場／前鋒）各自一條軌，避免門將與前鋒同尺度比較。
2. **陣容強度聚合（賽前 as-of）**：
   - `xi_strength` = 預期首發 11 人的位置加權評分均值（有官方陣容用官方，冇就用近 5 場出場率最高的 11 人）
   - `bench_strength` = 板凳前 5 人均值 → 直接回答換人問題：**板凳深度本身就是「換人不確定性」的特徵**
   - `availability_ratio` = 可用陣容評分 ÷ 該隊最強陣容評分（傷停停賽的量化版）
   - `minutes_uncertainty` = 預期首發名單的出場率方差（輪換多＝不確定性高）
3. **入模方式**：以上四項只作為**球隊層 LGB 的特徵**，不取代球隊 Elo。球隊 Elo 仍是主軸，球員層負責解釋「今場這支隊比平時強／弱多少」。

換人未知性的正式處理：
- 賽前預測用「預期首發」，並在前端明示這是預期陣容，同時顯示 `bench_strength` 與 `minutes_uncertainty` → 對應紅黃綠燈：官方陣容未出 = 黃燈（暫定），官方陣容公布（約 T-1h）= 綠燈（鎖定）。
- 回測必須用**賽前時間戳版本**的陣容，絕不可用賽後實際出場名單（否則就是 §1.4 第 2 條洩漏）。
- 深度不足的聯賽／賽季（球員分鐘數資料只有近 3 季）→ 分段報告，冇資料的區間退回純球隊層，與賽馬「新馬退回天喜足球ELO」同一邏輯。

Gate：球員層四項特徵加入後，RPS 必須顯著優於純球隊層版本，否則不上線（同賽馬 Stage14／Stage15 的處理）。

## 八、競品研究：data4mula.com 數據方程式（2026-09-13）

站點自 2016 年營運，Cloudflare 保護（高頻請求會即時 429／封鎖 → **唔可以爬，只作設計參考**）。導覽：足球賽事／足球賽果／賽馬賽事(Beta)／六合彩(Beta)／數據通行證／Telegram BOT。**與我們產品線幾乎重疊（足球＋賽馬＋六合彩），係最直接對標對手。**

### 8.1 賽事清單頁（值得直接抄的資訊架構）
一頁列全日賽事，約 40 個聯賽篩選，每場同時開多組欄位切換：
`主客和`、**`百家主客和`（多莊家平均）**、**`標準差 (SD)`**、**`變異係數 (CV)`**、`讓球`、`讓球主客和`、`入球大細`、`角球大細`、`第一隊入球`、`入球單雙`。
→ SD／CV 就是我們 feature_dict §13 `bookmaker_dispersion` 的產品化形態：**莊家間分歧愈大＝定價愈不確定**，既係特徵又係可以直接show給用戶的賣點。我們應該做：`p_impl` 的跨莊 SD／CV，並在前端做「市場分歧度」一欄。

### 8.2 單場分析頁的區塊清單（`/match/{uuid}/analysis`）
分頁：`馬會賠率`｜`賽事分析`｜`海外盤路`｜`賠率搜尋器`｜`陣容`。分析頁由上到下：
1. **陣容**：主客首發 11 人＋後備（含號碼、繁中譯名）、陣型（3-4-1-2 / 4-2-3-1）。
2. **近期數據統計**（近 3／5／10 切換）：進球、失球、被射門、角球、黃牌、犯規、控球率——主客並排對照。
3. **球證資料**：主裁對兩隊的勝和負紀錄、平均黃牌、**贏盤率**。
4. **進失球時段統計**（近 30／近 50）：1-15／16-30／31-45／46-60／61-75／76-90 六段的進球％與失球％，主客分開。
5. **盤路統計**（近 8 場）：贏／贏半／走／輸半／輸分佈。
6. **半全場統計**：主主／主和／主客／和主…九宮格分佈。
7. **入球統計**：0 至 6 球以上分佈；再分主場上／下半場、作客上／下半場。
8. **同聯賽歷史交鋒**與**兩隊近期戰績**：每場列勝負／讓球（W/L/WH/LH/D）／2.5 球大細／單雙四條盤路結果。
9. 明示「全部盤口、賠率均以香港馬會數據為主」。
繁中譯名覆蓋南美、墨西哥、女足等冷門聯賽，深度遠超五大聯賽。

### 8.3 對我們的可用結論
**照抄（產品層）**
- 「四條盤路歷史帶」寫法（勝負／讓球／大細／單雙逐場 W-L-D 色帶）——極高資訊密度、一眼可掃，同用戶想要的資訊密度要求一致。
- 進失球**時段分佈**（六段 × 主客 × 近 30／50）：呢個係我們 feature_dict 未列的一組，應補入 §3，命名 `goals_share_min_1_15` … `_76_90`、`conceded_share_*`，可直接支援上下半場盤口。
- **球證贏盤率**：補入 §12，`ref_home_cover_rate`。
- 多莊 SD／CV 市場分歧度（§13 + 前端展示）。
- 半全場、入球數分佈作展示層（我們模型本來就有 λ 比分矩陣，可直接生成，比佢哋純歷史頻率更強）。

**唔抄**
- 佢冇模型：全部係歷史頻率＋賠率呈現，**冇機率輸出、冇校準、冇對帳**。我們有 RPS／Brier／ECE 與逐場對帳＝差異點。
- 唔爬佢：Cloudflare 明確封鎖，且資料源本身係馬會＋商業盤口，我們應直接接馬會官方與正規源。

## 九、開源專案研究：Scodive/MatchPredict（2026-09-13）

倉庫規模約 3,800 行 Python、4.7MB 資料，Flask + Supabase + Vercel，MIT。定位為「五大聯賽數據 × LLM 分析平台」，含用戶積分／VIP／Admin 後台／串關策略引擎／中國體彩爬取。

### 9.1 實際架構（睇碼所得，與 README 宣稱有落差）
- **資料源**：football-data.org（賽果／賽程，`X-Auth-Token`）＋ The Odds API（h2h/spreads/totals）＋ Pinnacle 公開接口（README 稱即時 1X2）＋中國體彩爬取器。**與我們選定的免費組合幾乎相同 → 印證我們資料源選擇正確。**
- **模型層**（`scripts/models.py`，僅 162 行）：sklearn `RandomForestClassifier` / `GradientBoostingClassifier`，三分類 H/D/A，`GridSearchCV` 調參。**冇 Elo、冇 Poisson／Dixon-Coles、冇 xG、冇校準、冇集成。所謂「深度學習」在碼中不存在。**
- **特徵層**（`feature_engineering.py`，190 行）：只有主／客近 10 場入球、失球、勝和負率、近 5 場積分歸一化 `recent_form`，合計約 20 欄。遠少於我們 feature_dict。
- **「AI 智能模式」**（`ai_predictor.py`）：把兩隊名稱＋賠率塞進 prompt 叫 Gemini／OpenRouter 生成文字分析，**冇任何數值模型參與、冇機率校準**，只係 LLM 憑常識講。
- **回測／串關**：`parlay_predictor.py` 提供五種串關組合（信心穩單／博冷／獎金優化／平衡／價值挖掘），屬啟發式規則，非期望值最佳化。

### 9.2 四個致命方法論缺陷（正好對照我們 §1.4 洩漏清單）
1. **未來資料洩漏（最嚴重）**：`create_team_features()` 一次性用**全部已完成比賽**的最後 10 場算出每隊特徵，再 join 落每一場比賽。即係 9 月的比賽用到 5 月的資料——完全冇 as-of／`shift`。對應我們洩漏清單第 1、4 條。
2. **隨機 K-fold**：`train_test_split(random_state=42)` ＋ `GridSearchCV(cv=5)`。時序資料用隨機切分，訓練集含測試期之後的比賽。對應我們「嚴禁 K-fold」規則。
3. **標準化在全資料集上 fit**：`StandardScaler().fit_transform(X)` 在切分**之前**執行，測試期的均值／標準差洩入訓練。對應洩漏清單第 5 條。
4. **只報 accuracy**：`accuracy_score` ＋ classification_report，**冇 RPS、冇 Brier、冇 log-loss、冇 ECE**。README 宣稱「綜合測試準確率達到 90% 以上」，在 1X2 任務上（收盤賠率水準約 53–55% accuracy）**不可能成立**，係上述三重洩漏的直接後果。

### 9.3 對我們的用途
**可借鑒（工程／產品層）**
- 資料源組合印證：football-data.org ＋ The Odds API 已足夠起步。
- 產品設計借鑒：日期日曆瀏覽歷史預測、逐日命中率、Admin 手動同步、積分／VIP 分層（會員制參考）。
- 串關五模式命名（穩單／博冷／獎金優化／平衡／價值）——與我們賽馬「模型搏冷／市場穩陣」雙欄思路同源，足球版可沿用。

**絕不借鑒（模型層）**
- 佢個特徵管線同驗證方式全部違反我們 §1.4／§1.5 規則，**碼唔可以直接拿嚟用**。
- 「LLM 直接出預測」路線不採用：無法回測、無法校準、無法對帳。LLM 只可用於文字解釋層（把我們模型輸出寫成人話），不可作機率來源。

**最大教訓**：呢個專案正好係反面教材——**特徵管線做錯 as-of，回測數字就會靚到不真實**。我們 feature_dict 每個欄位都要標 `refresh` 與 `freeze` 凍結點，就係為咗防止呢件事。落地時每加一組特徵都要交出「凍結點快照」證明，唔接受單一 accuracy 數字。

## 十、開源專案研究：kochlisGit/ProphitBet-Soccer-Bets-Predictor（2026-09-13）

MIT、⭐573／fork 158、2026-04 仍在更新（v2 於 2025-11 發佈）。定位為**桌面 GUI（Tkinter）足球投注預測工作台**，非網站服務：下載 football-data.co.uk 全部聯賽 → 算滾動特徵 → 訓練多模型 → 特徵分析 → 由 footystats 解析未來賽程並輸出 Excel 預測。

- **資料源**：football-data.co.uk（賽果＋`AvgH/AvgD/AvgA` 多莊平均賠率，缺值退回 B365）＋ footystats（未來賽程解析）。**與我們選定的骨幹一致。**
- **特徵**（`src/preprocessing/statistics.py`）：27 欄，全部由主／客近 N 場滾動而來——主客勝負場數、入球／失球／淨勝球（主、客、主客差）、大勝／大敗場數（可設 goal-diff margin）、總主場勝率／敗率、射正、角球。`match_history_window` 與 `goal_diff_margin` 由用戶自選。
- **模型**：LR、LDA/QDA、NB、KNN、SVM、決策樹、隨機森林、XGBoost，以及自寫 TensorFlow 神經網（含 GRN／VSN 層，即 TFT 式變數選擇門）、AdaBelief／Adan／Ranger25／Lookahead 優化器；Optuna 調參。
- **目標**：只有 1X2（H/D/A）與大細 2.5 兩個分類任務。
- **可解釋性**：每個模型獨立 explainer（LR 係數、樹規則圖、KNN 鄰居、SVM 邊界、XGB gain）＋分析工具：Boruta 特徵篩選、impurity 重要度、相關矩陣、變異數、分佈、決策樹規則抽取。

### 10.2 三個真正值得抄的做法
1. **as-of 特徵管線做得正確**：`shift(1).rolling(n, min_periods=n).sum()`，逐季 `groupby('Season')` 分開計，並強制檢查日期單調遞增，否則直接 raise。同一組滾動邏輯我們 v0 可以照抄（比 MatchPredict 高一個檔次）。
2. **Profit Balance 指標**（`src/metrics/balance.py`）：由賠率反推「要幾高命中率才打得平」的**盈虧平衡命中率**，準確率高過它才算數學上有利。呢個係我們 gate 應該加的一條——RPS／Brier 之外，直接答「呢批選項賺唔賺得到」。
3. **機率校準內建**：`calibrate_probabilities` 預設 True，用 `CalibratedClassifierCV` 包住分類器。與我們賽馬已上線的 Platt scaling 同一路線，足球版沿用。
4. **Boruta ＋ 決策樹規則抽取** 可直接搬入 `/football/features` 頁：Boruta 給「呢個特徵是否真有用」的統計裁決（比單看重要度可靠），決策樹規則圖給用戶睇得明的「若 A 且 B 則傾向主勝」。

### 10.3 三個唔可以照搬的地方
1. **賠率直接入模**（最要留意）：`1`／`X`／`2` 三欄賠率**唔在 `non_trainable_columns` 內，即係當成訓練特徵**。違反我們 `market_beta = 0` 原則。照抄管線時必須把賠率欄剔出特徵矩陣，只留作基準線與對帳。
2. **驗證方式仍有時序問題**：預設 `cross_validation()` 用 `StratifiedKFold(shuffle=True)`——隨機切分時序資料；`sliding_cross_validation()` 才係時序（每 fold 取最近 k 段、以最新 N 場作測試）。我們只用後者思路（walk-forward），且 Optuna 調參目標函數目前掛在**隨機 K-fold** 上，唔可以照用。
3. **重採樣（SMOTE／NearMiss／IHT）改變機率分佈**：對「和局較少」做過採樣會令輸出機率偏離真實頻率，機率型產品唔應該用；我們靠校準而非重採樣處理不平衡。另外歸一化 fit 在 `preprocess_dataset` 內對整份輸入執行，我們要改成只在訓練段 fit。

### 10.4 落地決定
- v0 特徵管線採用其 27 欄滾動邏輯作 §3「歷史賽果（隊級滾動）」的參考實作，但**剔除賠率欄、逐季 as-of、只用 walk-forward**。
- gate 加入 **Profit Balance（盈虧平衡命中率）** 作輔助指標，主指標仍為 RPS。
- `/football/features` 頁加入 Boruta 裁決欄與決策樹規則圖。
- 神經網（GRN／VSN）與多種優化器屬 v2 研究層，v0–v1 不採用。

## 十一、開源專案研究：1canhhoa/sports-betting-toolbox（2026-09-13）

MIT、TypeScript、⭐135 但 **fork 869**（fork 遠多於 star、homepage 係一條 Telegram 連結、2026-06 才建倉），倉庫可信度需保留判斷。約 55 個檔案。

### 11.1 實際內容
分兩層，質素差異極大：

**A. 預測層（`src/predict/*`）——不可用**
- `predictMatch(homeTeam, awayTeam)` 只收兩個隊名，預設 `--source remote` 下載 GitHub 上**英超 2020 年**單季 CSV。
- `teamContext.ts` 算出的「特徵」只有：兩隊全季 W/D/L、入失球、H2H 場數、聯賽和局率。無 Elo、無 Poisson、無 xG、無賽程／傷停。
- **同樣犯 as-of 錯誤**：隊伍戰績由整份訓練表一次算出（只剔除 `fixtures` 標記行），非逐場往前推。
- `statistical.ts` 係手寫加權公式（`home.win*0.45 + away.loss*0.35`、先驗 42/26/32、H2H 權重上限 0.35），係啟發式規則，非擬合模型。
- **主力預測係 LLM**：`aiModel.ts` 把上述文字摘要塞進 prompt，叫 `gpt-4o-mini` 用 structured output 吐出 homeWin/draw/awayWin/confidence/reasoning。README 明言「AI step is required by default」，統計法只係 `--no-ai` 後備。同 MatchPredict 同一個毛病：**機率來自 LLM 常識，無法回測、無法校準**。而且它自報的 `confidence` 只係樣本數公式（`samples/16`），與預測準確度無關。
- 隊名匹配用 `includes()` 子字串比對，容易錯配（例如 Manchester City / Manchester United 類）。我們堅持穩定內部 ID ＋ 別名表就係防呢種錯。

**B. 策略／回測層（`src/strategies/*`、`src/platform/*`）——有參考價值**
呢層明顯係 Python `sports-betting`（georgedouzas）的 TypeScript 移植（`BaseBettor`、`OddsComparisonBettor`、`backtest`、`TimeSeriesSplit`、`ValueError` 命名一致），品質比預測層高：
- **`TimeSeriesSplit` 時序切分回測**：訓練段永遠在測試段之前，逐段前推，輸出每段 Training start/end、Testing start/end、下注日數、下注注數、**每注 yield %**、**ROI %**、期末資金。呢個正係我們要的 walk-forward 對帳表格式。
- **價值注（value bet）判定**：模型機率 × 賠率 > 1 才下注，回報用 `y*odds - 1` 結算。
- **`OddsComparisonBettor` 基準**：直接用多莊平均賠率取倒數再減 `alpha`（抽水估計）作機率——即係「去水市場基準線」，正好對應我們 S1 第三條基準。
- Redis 快取遠端 CSV、`platform/frame.ts` 自寫輕量 DataFrame，屬工程細節，我們用 D1＋Worker，唔需要照抄。

### 11.2 對我們的用途
**採用**
1. **回測輸出表格式照抄**：每段訓練期／測試期、下注日數、注數、每注 yield %、ROI %、期末資金。我們賽馬策略盈虧頁已有類似欄位，足球版沿用同一格式，前後端一致。
2. **價值注框架入 S1**：`p_model × odds_去水 > 1` 作為「是否值博」的判定，配合 ProphitBet 的 Profit Balance（盈虧平衡命中率），兩者合成足球版商業閘門：**RPS 過關（技術）＋ yield 正數（商業）**。
3. **`OddsComparisonBettor` 作 S1 第三條基準的參考實作**（多莊平均倒數減抽水）。賠率只出現在基準線與結算，**不入特徵矩陣**，維持 `market_beta = 0`。

**不採用**
- LLM 出機率（同 §9 結論一致，LLM 只做文字解釋層）。
- 單季資料、全季一次算戰績、子字串隊名匹配、手寫權重公式。
- 自報 confidence：我們的信心度必須由校準後機率與可靠度圖支撐，不可用樣本數公式充當。

### 11.3 三個開源專案合併結論
| | MatchPredict | ProphitBet | sports-betting-toolbox |
|---|---|---|---|
| as-of 特徵 | ✗ 全季洩漏 | ✓ shift(1) 逐季 | ✗ 全表一次算 |
| 時序驗證 | ✗ 隨機 K-fold | △ 有 sliding，預設仍隨機 | ✓ TimeSeriesSplit |
| 機率校準 | ✗ | ✓ CalibratedClassifierCV | ✗ |
| 商業指標 | ✗ 只 accuracy | ✓ Profit Balance | ✓ yield / ROI / 價值注 |
| 賠率處理 | 入模 | 入模（要剔） | 只作基準與結算（正確） |
| 可借鑒 | 產品層 UI | 特徵管線＋校準＋Boruta | 回測表＋價值注＋去水基準 |

**三者合起來剛好補齊我們 S1 缺的一塊**：ProphitBet 給滾動特徵與校準，sports-betting-toolbox 給時序回測表與價值注結算，MatchPredict 只作反面教材。三個都無一個做到**凍結預測＋公開對帳**，呢個仍然係我們的差異點。

## 十三、競品研究：7M（news.7m.com.cn，2026-09-13）

老牌華文體育數據站（2003 年起），足球／籃球／棒球／美足／網球即時比分＋資料庫＋新聞。我們看的 `/list/5/` 是「賽前分析」欄，分頁：國際足球／中國足球／轉會動態／賽前分析／7M製造／賽事推介／足球情報。

### 13.1 授權定性（先講結論：不可爬）
`data.7m.com.cn` 頁尾明文：「本站呈現的所有資料均由 7M 工作團隊編輯發布，版權所有，嚴禁竊為己作；未經授權切勿轉載或建立鏡像……如欲轉載、建立鏡像、選用或其他任何商業用途，請聯繫商談。」賽程頁亦標明「以上數據由 SportsDT 提供」——即佢自己都係二手授權。**定性：與 Sofascore／Flashscore 同級，不進生產、不爬取。**

唯一正規途徑係佢個 **「免費調用」計劃**（`freelive.7m.com.cn/apply_jt.shtm`）：填網站名稱／時區／樣式，生成一條調用 URL，可嵌入即時比分、滾動比分、積分榜、新聞。但本質係**帶佢品牌與廣告的嵌入式頁面，不是可入庫的原始數據**，做不到特徵計算、回測、對帳，亦會令我們頁面掛住第三方廣告。**判斷：不採用**（最多作應急備援顯示，需先申請授權）。

### 13.2 真正有價值的兩樣（作參考，不複製）
**一、繁體港式譯名慣例對照**
佢繁體版用的正是港式譯名：熱拿亞、費辛隆尼、拉素、阿特蘭大、卡利亞里、甘堡爾、幸運薛達、阿積士、伊高斯、高寧根、川迪、海牙、勒哈弗爾、昂熱、史特拉斯堡、摩納哥——與馬會足球盤慣用譯名體系一致（例如「拉素」而非「拉齊奧」、「阿積士」而非「阿賈克斯」）。同一頁的簡體段落則用「拉齐奥／亚特兰大」，正好示範**同一支球隊在簡繁兩套體系下完全不同名**。

這確認了我們 `team_names` 表的設計必要性，並要多加一欄：
```
team_names(team_id, name_en, name_zh_hk /* 馬會優先 */, name_zh_cn, alias[], source, verified_by, verified_at)
```
其中 `name_zh_hk` 以**馬會官方足球版譯名為唯一權威**，7M 繁體只作人手核對時的旁證（受版權限制，不可整批抄錄入庫）；`name_zh_cn` 同時保留，因為未來若接內地源（如 TheSports、SportsDT 系）回傳的是簡體名，需要靠這欄做映射對齊。無把握者一律入「待審告警」。

**二、賽前文章的資訊結構（值得照學的寫法）**
每篇約 150–300 字，結構高度固定：
1. 標題用港式雙關（「費辛隆尼乘勇再捧」、「拉素博『和』得『米』」、「阿特蘭大『半和』打卡」）；

4. 右側「場外動態」短訊流（轉會、傷情、教練談話），每條約 20 字＋[詳細]。

→ 這正是我們 `/football/match` 缺的「人話賽前簡報」模板。落地做法：**由我們自己的資料生成**（陣式來自賽前陣容源、傷停來自 Transfermarkt 開放集／TheSports、入球助攻來自 Understat／FBref），再由語言模型按上述四段式寫成繁體港式文字；盤口推介一欄改為**我們的模型輸出＋紅黃綠燈**，並附凍結時間。與 §9 結論一致：語言模型只做文字層，機率一律來自可回測模型。

### 15.1 它的方法論（與我們高度重合，可作外部佐證）
`/tw/algo/` 寫明五步管線：抓取歷史數據 → 清理 → 特徵工程 → 模型訓練 → **拿模型勝率比對即時賠率找正期望值**。資料源用 Basketball-Reference 與 stats.nba.com，300 萬筆以上。三點與我們既有做法完全一致，可作獨立佐證：

3. **跨賽季 Elo 回歸**：`Elo_next = R × 0.75 + 0.25 × 1505`，新賽季把上季期末分向聯盟平均回歸 25%。→ 我們足球ELO要照做（賽馬引擎現時無跨季回歸，值得一併回測）。

### 15.2 它的公開驗證頁（我們該學的呈現方式）
`/tw/ai-model-performance/`：
- 三個大數字：最佳模型勝率 77%（專家高信心場）、去年累積 +1,210 單位、即時監測 12,686+ 場、模型迭代 52 次。
- **有一整段叫「79% 勝率的誠實定義」**，明講三件事：79% 只係「AI 精選高信心場次」的命中率、不是每注都贏；+1,240 單位係長期累積、中間一定有輸的日子；並在註腳承認**「過去預測」全部推薦的整體命中約 50%**，79% 係再篩到三星高信心後的數字，「兩個數字不衝突」。

**我們要照學的三樣**：①「誠實定義」段落——把全體命中率與精選後命中率並列，避免只掛一個漂亮數字（我哋四揀命中率頁應加同類說明）；②校準曲線我們已有，**再補資金曲線（含最大回撤）與學習曲線**；③指標表加 **最大回撤、平均賠率、盈虧比** 三欄，與 §11 的 yield/ROI 併成同一張商業對帳表。

### 15.3 要保持懷疑的地方
- 它把主力模型叫 BERT，理由是「BERT 處理時間序列能力遠超 LSTM」、能識別「誘盤」——這是**行銷式論述**，未提供架構、樣本切分或損失函數；註意力熱力圖只寫「示意」。
- 「1,500+ 特徵／場」、「v4.8 比 v4.2 多 13 個百分點勝率」無回測協議支撐；勝率／ROI／回撤全部標「回測示意」。
- 定價：入門 199／標準 299／專家 499 **美元每月**（年繳付 10 個月），一次性購買不自動續訂，專家方案有「未獲利免費續期保障」。→ 對照 tipsme 的 HK$688/年，兩者相差近 30 倍，說明**同一市場可以有極端不同的定價帶**；我們走「可核查對帳 ＋ 低價」路線時，可以引用它的「未獲利免費續期」作為信心保證機制參考。

**結論**：方法論與我們一致（Elo 為主、相對化、去洩漏、正 EV 才下），呈現方式值得抄，但績效數字缺回測協議，不可當基準；我們的優勢仍是**真實逐日對帳而非回測示意**。

## 十七、技術文章：《太硬核！用大數據技術預測足球勝率》（騰訊工程師，2022-12，CC BY-SA）

歐洲五大聯賽 1X2 預測全流程實作記錄。**這是我們研究過最誠實的一篇**——它明確算出「按模型預測直接投注長遠必虧」，然後才談怎麼補救。

### 17.1 它的做法
- 資料：2010-07 至 2015 年五大聯賽賽果 ＋ **17 家莊家的初賠**。特徵 = 球隊基本面 **17 維**（實力、賽前狀態、對戰歷史、場地效應、攻防能力五類）＋ 賠率 **51 維**（17 家 × 勝平負）。只用初賠，理由是各家終賠沒有統一時間標準（→ 正合我們「凍結點必須可定義」的原則）。
- 模型：英超 LR 準確率 38.18% → SVM 51.23% → 隨機森林 53%+ → 再用 DNN 逐層預訓練取隱層輸出當新特徵、與非線性模型 ensemble，最佳 **(NN+SVM) 54.55%**。
- **特徵重要度結論：在隨機森林下，17 維球隊基本面權重普遍偏低，起作用的主要是賠率特徵。**
- 法甲例外分析：自建「聯賽混沌程度」指標（按積分排名給 20…1 分 → 算每隊近 10 季排名方差 → 全隊平均），法甲混沌度遠高於其餘四大聯賽，故準確率最低。杯賽＝混沌度更高的「聯賽」，場次少、歷史對戰弱，更難預測。
- 比分預測：泊松只建模 λ 取最大概率比分（作者自稱「很強、很朴素的假設」）；或當 25 類（5×5）Softmax 多分類，因歐洲杯 97% 場次入球數 <5。

### 17.2 最有價值的一段：盈利門檻與概率分段投注
單場固定注玩法下，長期利潤 > 0 的條件是 **「預測準確率的倒數 < 命中場次的平均賠率」**（1/precision < 平均賠率）。實測最佳模型：準確率 54.55%、倒數 1.8332、命中場均賠率 1.8008 → **不滿足，長遠必虧**。

補救不是加特徵，而是**按預測機率分段找可盈利區間**：英超在 `p < 0.4` 與 `p ≥ 0.9` 兩段滿足盈利式，只在這兩段出手（英超出手率約 20%，法甲僅 7%）；其餘四大聯賽亦各有類似可盈利機率段。作者同時誠實列出三個限制：只在約 300 場測試集驗證過、出手率偏低、賠率波動令盈利率不穩。

### 17.3 落地決定
1. **盈利門檻式納入足球商業閘門**：`1/precision < 命中場均賠率`。這條與 §10 的 ProphitBet Profit Balance、§11 的 yield/ROI 是同一件事的三種寫法，統一成一張表：技術（RPS／Brier／ECE）＋ 商業（盈利門檻、yield%、ROI、最大回撤、盈虧比）。
2. **按機率分段找可出手區間**，並在產品上顯示為「今日出手／不出手」與出手率——這正好接上我們賽馬已做的分段機率校準（只調機率、不改排名），差別是這裡用來決定**是否推薦**，而非改排名。
3. **「聯賽混沌度」指標照做**：按積分排名方差算每個聯賽的混沌度，用途有二——排定我們擴展聯賽的優先次序（先做低混沌度聯賽），以及在賽事頁顯示「本聯賽可預測性」，作為紅黃綠燈的其中一個降級理由。
4. **它的「賠率特徵權重最高、基本面偏低」結論不改我們原則**。原因：它的基本面只有 17 維粗特徵（無 xG、無陣容、無傷停、無疲勞），賠率自然贏；而賠率入模等於把莊家答案抄一次，模型永遠只能貼近市場、無法產生獨立信號，亦無法做「對照市場」這個產品賣點。我們維持 `market_beta = 0`，但**把它的 51 維初賠特徵版本作為「with_odds 對照軌」離線基準**（特徵字典第 13 章早已規劃 no_odds／with_odds 分軌），用來量度我們的 no_odds 模型距離市場還有幾遠。
5. 不採用：DNN 逐層預訓練（2012 年代做法，現以 LightGBM＋校準取代）、剔除「爆冷奇異樣本」再訓練（會系統性低估冷門，違反我們搏冷定位）。

- 方法論停在概念層：資料源只泛稱「賽前數據／賠率水位／賽中技術統計／新聞社媒情緒」；特徵分四層（賽季級、近 6 場與換帥、賽前賠率偏移與傷停、賽中控球射門跑動），全無公式或欄位定義；模型只點名「多模型／多智能體融合、stacking／貝葉斯模型平均、蒙特卡洛比分模擬」，無算法名、無超參、無架構。
- **完全沒有訓練／驗證切分說明**。作者只在「常見誤區」建議讀者自己做交叉驗證與後驗校準，卻沒描述自己做過什麼。
- 作者自認限制：不要把單季成功率當長期法則、不要盲信模型輸出、勿忽視樣本偏差與時間外推風險，並自認社群公布的回測準確率「需謹慎查看原始回測方法與樣本選擇」——等於自己都不信那些數字。

### 19.2 判定
- **拒絕**：賠率作為特徵輸入（違反 `market_beta = 0`）；任何 80%／82.3% 類宣稱（先射箭後畫靶）；照搬其「多智能體融合」架構聲稱（不可審計、不可複現）；依賴或參照 worldliveball 這類來源不明的第三方工具。
- **可取（僅工程理念，需自行嚴謹落地）**：多時間尺度特徵分層（賽季／近況／賽前／賽中）對應我們的 as-of 凍結設計；紅牌／傷退等突變事件觸發即時重新加權的想法，留作將來滾球模組靈感；蒙特卡洛輸出比分分布而非單一結論，與我們用 RPS 評機率預測方向一致，可作呈現層參考；每次預測存輸入快照＋賽後複盤留痕——這點我們的凍結預測機制已在做，繼續強化 audit trail。

1. **只講命中率，不講校準、不講回報**：全站無 RPS／Brier／ECE，無 ROI／yield／最大回撤，無樣本顯著性或置信區間。「66.6%」亦未定義是哪種盤口的口徑（疑為多盤口混合）。命中率高 ≠ 有賺——這正是 §17 盈利門檻式要回答的問題。

3. **不可竄改只靠 GitHub commit 歷史**，屬自我聲明，無第三方或密碼學證明。
4. **中文完全走簡體大陸路線，零香港在地化**。
5. **定價收埋**，與「透明」定位自相矛盾。

1. **對帳頁照它的三段式版面做**：KPI 卡（總命中率／高信心命中率／總場次／追蹤年期）＋ 月度與近 14 日時序圖 ＋ 可下載原始 CSV。但我們的 KPI 卡要同時放 RPS、ECE、yield%、最大回撤，並依 §15 寫「誠實定義」段落（全部推薦 vs 精選高信心並列）。
2. **凍結證明升級**：除了每日 commit 時間戳，加上預測快照 hash 與凍結時間，對帳頁可逐場展開比對。
3. **每日限量免費貼士**作獲客漏斗，可採用。
4. **三個直接差異化方向**：公開校準指標與回報率（不只命中率）、地道繁體＋香港馬會譯名、定價公開透明。
5. 不採用：單一命中率作主打指標、事後多盤口擇優、隱藏定價、照搬其簡體詞彙庫。

## 二十二、產品原則與四項待驗證特徵假設（用戶觀察，2026-09-13）

### 22.1 透明度原則（寫入公開頁，不可打折）
**一切都是透明的：過去的預測全部公開，包括差的預測與虧損期，不隱藏、不刪除、不事後修改。**
落地要求：每場預測凍結時保存快照 hash ＋ 凍結時間；對帳頁預設顯示全部歷史（不是只顯示命中的）；虧損期在資金曲線上照樣顯示，並標最大回撤；「精選高信心」與「全部推薦」兩條線並列（見 §15、§20）。這一條同時是我們對 §18 AutoBetSoft、§20 NerdyTips 的直接差異點。

### 22.2 四項假設 → 特徵設計（全部要回測驗證，不預設成立）
1. **天氣影響被低估，一般雨／風已足以拖累重控球球隊。**
   → 不做「天氣好／壞」單一欄，做**交互特徵**：`precip_mm`、`wind_kph`、`temp_c` × 球隊風格向量（控球率、每場傳球數、短傳比、場均直塞）。資料用 Open-Meteo 歷史逐小時（1940 至今、免 key），按開賽時間與場地座標 as-of 對齊。預期效果：控球型球隊在高風速場次的 xG 折損 > 直接型球隊，若回測見不到就照實記錄為無效假設。
2. **連勝好看，過濾對手強度之後就未必。**
   → 所有近況特徵一律出**兩個版本**：原始版（近 5／6／10 場勝率、進失球）與**對手 ELO 加權版**。再加一項 `form_inflation = 原始版 − 加權版`，直接量度「假連勝」程度，並在賽事頁顯示為「這波連勝的對手有幾強」。這同時修正 §10 ProphitBet 那 27 欄滾動特徵的最大盲點（它完全不計對手強度）。
3. **莊家對傷病的評估似乎偏低估。**
   → 建 `absence_impact = Σ(缺陣球員 ELO 貢獻 × 近期上場分鐘佔比)`，按位置分開（後防／中場／前鋒），並加隊長／首選門將旗標。**驗證方法：用市場賠率隱含機率對 `absence_impact` 做殘差回歸**——若殘差與缺陣強度顯著相關，即證實市場低估，該處就是我們的 alpha 來源。注意：這條**只在離線對照軌做**，賠率不會進特徵矩陣（`market_beta = 0` 不變）。這亦是我們必須取得可靠傷停源的理由（§21 SportsAPIPro 無傷停端點，故不採購）。
4. **舊對戰數據（>3–4 年）幾乎無價值。**
   → H2H 特徵一律加**指數時間衰減** `w = exp(-Δt / τ)`，`τ` 由回測選（候選 180／365／540／730 日），不拍板定死。同時保留「近 3 次對戰」硬窗口版本作對照。這與 §11 sports-betting-toolbox 把 H2H 權重上限設 0.35 的做法同向，但我們用衰減而非硬上限，並以回測決定。
   附帶結論：既然舊 H2H 無價值，`/football/match` 的歷史交鋒區塊要標明每場的時間權重（近場深色、舊場淡化），唔好將 10 年前嘅比分同上季同等呈現。

### 22.3 驗證閘門
以上四項每項都要交：walk-forward 前後 RPS／Brier／ECE 對比、凍結點快照證明、以及特徵重要度與方向是否符合假設。**過不了就照實在開發者日誌寫「假設不成立」，唔會為咗故事好聽而保留。**

## 二十四、資料源審查：Understat（understat.com，2026-09-13）— 合規紅旗，不排程抓取

### 24.1 兩個必須先講的障礙
1. **`https://understat.com/robots.txt` 實測內容就係：`User-agent: *` ／ `Disallow: /`——全站禁止自動化抓取，冇任何 Allow 例外。** 雖然 PyPI 上有大量開源套件（`understat` 181★ MIT、`understatAPI` MIT）技術上做得到，但**佢哋全部都係違反站方 robots.txt 意願**。按我們既定原則（不爬 ToS／robots 禁止的站），**Understat 由「免費組合第一梯隊」降級為「需先取得書面授權才可用」**。站方冇獨立 ToS 頁，亦無速率指引與商用聲明。
2. **2025-12 起站方已改前端載入架構。** 實測三類頁面：`match/9457` 只剩 `match_info`，**`shotsData` 已不在原始 HTML**；`league/EPL` 已無 `datesData`／`teamsData`；`player/2097` 只剩極簡 `player` 物件，`groupsData`／`matchesData` 皆無。understatAPI issue #15（2025-12-12）證實同一件事，原有解析全數 `JSONDecodeError`。→ 即係**要靠瀏覽器自動化攔 XHR 才拿到明細**，維護成本與不穩定性大幅上升，而且更加明顯係繞過站方意願。

### 24.2 它的資料值（記錄下來，作日後採購同類 xG 源的規格書）
- 覆蓋 6 個聯賽：EPL／La_liga／Bundesliga／Serie_A／Ligue_1／RFPL，**2014/15 季起**。賽後數小時入帳（無 SLA）。**冇港超、冇亞洲賽事。**
- 賽事層 `match_info` 實測欄位：`h_xg`／`a_xg`、`h_shot`／`a_shot`、`h_shotOnTarget`／`a_shotOnTarget`、`h_deep`／`a_deep`（deep completions）、`h_ppda`／`a_ppda`、`h_w`／`h_d`／`h_l`、`date`、`league_id`、`season`。
- 射門層 `shotsData`：`minute`、`player_id`、`h_a`、`xG`、`situation`（OpenPlay／SetPiece／DirectFreekick／Penalty）、`shotType`（LeftFoot／RightFoot／Head／OtherBodyPart）、`lastAction`、`X`／`Y`（0–1 標準化座標）、`result`、`player_assisted`。
- 球員層：xG／xA／npxG／xGChain／xGBuildup、分鐘區間拆分、位置拆分。
- **PPDA、deep completions、逐球 xG 分佈與座標**這三組正是我們最想要的風格特徵（直接餵 §22.2 第 1 項天氣 × 控球風格交互特徵）。**所以 xG 源的採購規格就照這張表寫，去要求 FootyStats／TheSports 或 StatsBomb open data 對得上。**

### 24.3 as-of 使用紀律（無論將來用邊個 xG 源都適用）
Understat 全部數據都係**賽後**產物。做賽前特徵時：
1. 以該場 `date`（UTC）為時間錨點，只用**該場之前**已完場賽事的滾動 xG／xGA／PPDA（過去 5／10 場），**絕不可把該場自身的 `h_xg`／`a_xg` 當賽前特徵**（look-ahead 洩漏）。
2. 嚴格按比賽時間排序切分，**不可用抓取時間代替比賽時間**。
3. 它冇賽前陣容、冇傷停 → 陣容與傷停必須另源（API-Football 或 TheSports）。

### 24.4 決定
1. **不排程抓取 Understat。** 改為：先寄信問站方可否授權（或有無官方匯出），未有書面回覆前不做任何排程性抓取。
2. **xG 主源改走這條次序**：StatsBomb open data（明確開放授權，做歷史與模型校準）→ FootyStats API（付費、含 xG）→ TheSports。Understat 只作**人手抽樣核對**用途，不入生產管線。
3. 把 §24.2 那張欄位表寫入特徵字典，作為評估任何 xG 供應商的驗收清單（有冇 PPDA、有冇 deep completions、有冇逐球座標與 situation／shotType／lastAction）。

## 二十五、競品研究：PredictApp／RWI 模型（LinkedIn 文章＋官方 blog，2026-09-13）

來源：Daniel Roiz Walss（PredictApp 創辦人）LinkedIn 長文《Why Most Soccer Prediction Models Ignore 1 in 4 Outcomes》（2026-03-24）及 blog.predictapp.io。

### 25.1 核心論點：和局被系統性忽視
- 佢哋 34,042 場樣本實測和局率 **25.4%**，但莊家把和局列為最可能結果的場次只有 **1.3%**——唔係預測失敗，係結構性決定：莊家目標係管理風險敞口同流水，唔係最大化命中率。
- 推論同我們既有原則一致：**賠率隱含機率在和局上系統性偏低**，所以賠率只可做基準線，不可入模；同時和局係「模型 vs 市場」最有機會跑出嘅位置。

### 25.2 RWI 架構（同我們設計高度重合，等於獨立驗證）
- 球隊評分**拆四維**：主場進攻、主場防守弱點、作客進攻、作客防守弱點（唔合併成單一數字）。
- 對數空間計預期入球：四維狀態 ＋ 聯賽入球基線 ＋ 主場優勢先驗 ＋ **陣容修正**。RWI＝賽前預期淨勝球，只係強度訊號，唔係最終機率。
- **球員級處理同我們 §6 決定幾乎一樣**：每名球員評分用收縮公式向所屬位置均值收縮、按上場分鐘加權（30 分鐘歷史的球員信任度遠低於 1,000 分鐘）；兩隊陣容分差以**乘性修正**作用於預期入球。
- **線上更新**：目標值＝實際入球 與 xG 的混合（平滑爆冷）；殘差經有界函數變換先更新球隊狀態，再有跨主客場追趕係數 ＋ 向零輕微收縮；球員評分按出場權重從淨勝球殘差更新。
- 下游機率層：**Ordered Logit（三類有序分類）＋ CatBoost 混合**，特徵＝RWI 輸出 ＋ 聯賽上下文。

### 25.3 誠實度亮點（值得照抄態度）
- 明寫「整體指標同莊家基準之內的噪音範圍——**呢個先係正確基準：唔係總體跑贏市場，係追平市場最強訊號**」。Pearson 0.330／Spearman 0.323（burn-in 後 0.350／0.339）、主場入球 MAE 1.005／作客 0.850、八季命中率 50.1%、log loss 1.019——全部照實公開。
- 勝出位喺 **macro F1 同和局召回率**（模型 1.97% vs 莊家 <1%）。
- **但首頁照樣寫「91% safer read／74% exact pick」**——定義含糊的營銷數字，同 Mysports 的「79%」同一套路。我們的「誠實定義」段落必須堅持唔學呢啲。
- 免費對賽統計全開放，靠產品其他層變現。

### 25.4 我們執行什麼
1. 對帳頁加**和局召回率（draw recall）**做次要指標（主指標仍 RPS），直接量化「我們幾認真對待 25% 的賽果」。
2. ELO 更新目標值測試「實際入球 × xG 混合」版本（回測先過關先好上）。
3. 有序分類（Ordered Logit／rank-consistent 輸出）列入 LGB 之外的對照模型——佢天然適合 1X2 有序三類。
4. 維持：球員評分按分鐘收縮→聚合成球隊層（不加總），同 RWI 做法一致，呢條路被獨立團隊驗證過。

## 二十六、資料源審查：SoccerStatsHub（soccerstatshub.com，2026-09-13）— 不作資料源；方法論頁係免費教科書

### 26.1 背景判斷
用戶轉述站方自述「建在 FootyStats 付費數據之上、盡量免費」。實測結論：**它唔完全免費**——首頁明寫「免費只係樣本場次，Premium 解鎖全部聯賽、完整賽事詳情、multis、BTTS／大 2.5 研究頁同完整預測引擎」（即 freemium）。而且佢嘅內容本質係 **FootyStats 授權數據的再發布**：抓佢等於繞過佢嘅條款同時侵犯 FootyStats 授權，**定性同其他付費輸出站一樣：不爬取、不進生產、不作資料源**。我們要 FootyStats 數據就正路買佢自家 API（§14），價錢本來就平。

### 26.2 它的方法論頁——等於把我們規劃的管線公開寫了一次（獨立佐證）
- **Lambda 管線**：聯賽入球基線分拆主客 → 攻擊強度 × 對手防守弱點 → 原始預期入球。
- **少於 10 場向聯賽均值收縮**（季初冷卻）——我們 ELO 跨季回歸之外的另一個冷卻機制，採用。
- **缺陣／陣容微調 lambda**（對應我們缺陣強度指數）；**xG 效率回歸調整**（實際入球 vs 機會質素）；**新教練旗標**短期上調預期（新特徵，記入字典）；洲際／國際賽事**加重市場賠率混合**（佢咁做，我們唔跟——違反賠率零權重，只做紅黃綠燈降級理由）。
- **Poisson 比分矩陣（0–5 各邊）＋ Dixon-Coles 低比分修正（0-0／1-0／0-1／1-1）** → 歸一化 ＋ 輕校準 → 一次過派生 1X2／BTTS／大小 2.5／最可能比分。**預測比分＝矩陣最高機率格，唔係另估**——這條「單一矩陣派生全部盤口」的紀律照抄，保證各盤口概率互相一致。
- 模型機率 與 莊家隱含機率並排 ＋ 「價值百分比」顯示（等於我們的市場對照欄）。

### 26.3 值得抄的產品位
1. **Market Reliability 頁**：按盤口統計市場可靠度——我們可在對帳頁加同類視角。
2. 統計榜 SEO 叢集做得齊：BTTS 球隊榜、BTTS 賽事榜、最高入球聯賽、大 2.5 球隊榜——同我們 §12 長尾榜頁策略完全一致，繁體版空白仍在。
3. 「無莊家 affiliate 連結」做信任賣點——我們同樣適用，可寫進關於頁。

### 26.4 決定
- **不作資料源**（FootyStats 再發布，雙重授權風險）。FootyStats 正路採購位不變。
- 特徵字典新增：新教練旗標、xG 效率回歸調整、<10 場向聯賽均值收縮。
- 引擎規格加一條硬紀律：**所有盤口（1X2／BTTS／大小球／波膽）必須由同一個比分機率矩陣派生**，唔准各自獨立估。

## 三十三、三條紀律補入（2026-09-13，源自「強盛機器學習」CSDN 206 篇通讀）

### 33.1 洩漏紀律：任何要用到全序列嘅變換，都必須逐時點只用歷史
對方點名 WOS／知網大量 EMD／VMD 論文係「訓練同測試集一齊分解」，測試段資訊倒流入訓練，
造成虛假高精度。我們冇用 VMD，但同一條錯有三個等價入口，全部封住：
- 滾動特徵（近十場入失球、射門、角球、牌）只可以用嚴格早於開賽時間嘅場次。
- 標準化／z-score 嘅平均數同標準差，只准由訓練段估出，唔可以用全樣本。
- Elo、攻守係數、校準器（向量標度／保序）一律逐季 walk-forward 重擬合，唔可以一次擬合全歷史。
違反其中任何一項，回測成績即作廢。

### 33.2 逐輪凍結：唔可以一次批量算完整季當「賽前預測」
「超前 24 步」實質只係一次性輸出 24 行同真值對比，唔反映誤差累積；
對應到足球就係一次過批算整季特徵。規矩：預測必須逐輪（逐個比賽日）生成並凍結，
帶當時嘅模型指紋同特徵指紋，之後唔改。回測亦要模擬同一節奏。

### 33.3 呈現升級：機率區間 ＋ 逐場特徵貢獻
現時只出點機率。補兩樣：
- **機率區間**：以自助抽樣（bootstrap）或三軌分歧度出 90% 帶寬，卡內以細字標「±x 個百分點」，
  帶寬闊即代表引擎自己都唔肯定，比一個假精確嘅單點誠實。
- **特徵貢獻**：LGB 出 SHAP，逐場列前三至五項推高／推低嘅因子（例：主隊休息多 3 日、客隊近五場失球升）。
兩項都只作解釋層，唔改變排名，亦唔會引入賽後資料。

### 33.4 明確唔抄
群體智能優化算法（每月一隻新命名算法）調超參數——喺我們嘅訊噪比下係過擬合機器；
以及自報 R²／MAPE 而冇前瞻凍結對帳嘅成績呈現方式。

### 35.4 抓取範例與實作紀律

用戶提供嘅 Python／JavaScript 範例以 football-data.org 為目標，核心正確：帶 `X-Auth-Token`、檢查 status、解析 `teams[].crest`。我哋實作時要額外守以下紀律：

1. **Rate Limit**：免費 API 通常每分鐘 10 次或每日 100 次，排程必須加 `time.sleep`／退避，並設併發上限（參考 §32.1 golazo）。
2. **永不即時打上游**：用戶請求不直接觸發 API 呼叫，只讀已正規化嘅本地表（參考 §32.2 上游契約）。
3. **失敗保留舊快照**：排程失敗時保留上一份有效 `crest_url`，並標 `stale`。
4. **新鮮度入表**：`sync_states` 記錄最後成功時間，看門狗監察。
5. **不抓禁止站**：Wikimedia Commons 雖可讀，但隊徽多數係商標；下載站無授權；一律不批量抓取。

參考實作片段（Python，用於排程倉，非前端）：

```python
import time, requests, os
API_KEY = os.environ["FOOTBALL_DATA_TOKEN"]
URL = "https://api.football-data.org/v4/competitions/PL/teams"
headers = {"X-Auth-Token": API_KEY}
resp = requests.get(URL, headers=headers, timeout=15)
resp.raise_for_status()
for team in resp.json().get("teams", []):
    canonical_id = mapping.to_canonical(team["name"])  # 經 team_mapping
    upsert_crest(canonical_id, source="football-data.org", url=team.get("crest"))
    time.sleep(6)  # 免費層保守速率
```
